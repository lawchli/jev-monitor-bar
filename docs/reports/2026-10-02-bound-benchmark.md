# 状态聚合表限量维护基准

日期：2026-10-02。主机 Linux x64，Node 22.23.2。只测 `applyEvent` 的表限量维护，不代表磁盘、HTTP、Electron 或模型推理的吞吐量。

命令：`node --import tsx scripts/loadtest/bound-bench.mts --events 10000 --repeat 3`。旧版用 `--module` 加载 `7aa03dd:src/state.ts` 的只读副本。每种场景先预热、再做三轮，取每事件微秒数的中位数；表预填充不计时。测试时还有其他 agent 运行，属于开发环境基准。

| 场景 | 旧版 μs/事件 | 新版 μs/事件 |
| --- | ---: | ---: |
| 已满决策表，每条新增字符串 ID | 37.668 | 1.048 |
| 已满决策表，更新已有 ID | 12.283 | 0.094 |
| 已满决策表，每条新增整数形态 ID | 26.045 | 0.921 |
| 已满尝试表，每条新增 ID | 39.533 | 0.808 |
| 50 个决策键，更新已有 ID | 1.436 | 0.102 |

两版各场景的最终键数、首尾键和 `limited` 一致。四项状态限量回归与回放测试通过；独立审计又比较了 20,000 条随机事件的完整状态、复制表和 75 次随机回放跳转，结果见 `2026-10-02-audit-desktop.md`。

实现用 WeakMap 缓存键计数与淘汰顺序，避免每个事件都枚举 500 个键；保留 `Object.keys` 的整数键优先语义，复制后的回放表首次出现时单独建立缓存。运行、决策、尝试及事件窗口的原有容量上限没有增加。
